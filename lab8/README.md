# Lab 8 - Security and Policy as Code

I configured tfsec v1.28.14 in `.github/workflows/lab8-policy.yml` to scan Terraform on pull requests using `--minimum-severity HIGH`. Through GitHub Settings > Branches, I made `tfsec` a required status check on main and required changes to go through a pull request. When tfsec detects a HIGH or CRITICAL finding, it returns exit code 1, causing the required check to fail and preventing the merge. A successful scan returns exit code 0. The branch protection configuration is documented in `evidence/required-status-checks.json` and `evidence/required-status-checks.png`.

I deliberately changed the SSH ingress rule to `0.0.0.0/0` and disabled encryption on the EBS scratch volume. Tfsec reported `aws-ec2-no-public-ingress-sgr` as CRITICAL and `aws-ec2-enable-volume-encryption` as HIGH. Opening SSH to everyone allows anyone on the internet to attempt to connect, including attackers attempting brute-force attacks. An unencrypted volume also increases the risk of data exposure if its contents or snapshots are accessed without authorization. PR #17 was blocked by the required tfsec check. I fixed both findings by restoring the validated `/32` administrator CIDR, setting `encrypted = true`, and restoring the customer-managed KMS key. The required checks then passed and the merge button became available. The overall PR status was UNSTABLE rather than CLEAN because an unrelated, non-required Lab 3 deployment check lacked AWS credentials. The security gate itself passed. Evidence is available in `evidence/tfsec-before.txt`, `evidence/tfsec-after.txt`, `evidence/pr-mergeable-blocked.json`, `evidence/pr-mergeable-passing.json`, `evidence/pr-blocked.png` and `evidence/pr-passing.png`.

The IAM policy in `policies/lab8-deploy-policy.json` is narrower than PowerUserAccess. It restricts compute operations to us-east-1, limits S3 access to Lab 8 bucket names, and does not allow disabling CloudTrail logging. It also restricts iam:PassRole to LabRole for EC2. Although the handout expected an AccessDenied error when creating the policy, my workstation's LabRole unexpectedly permitted the operation. I did not attach the policy and deleted it successfully, following the alternative instruction in the handout. The actual result is recorded in `evidence/iam-create-policy-accessdenied.txt`. I accepted one MEDIUM finding, `aws-s3-enable-versioning`, because the proposed bucket would only store reports that can be regenerated by CI. The exception is signed and dated November 21, 2026 in main.tf. I would remove it if the bucket began storing unique or audit-critical data. I also ran `gitleaks detect --source . --log-opts="--all" --redact=100` with JSON reporting to scan Git history rather than only the working directory. Gitleaks scanned 53 commits, found no secrets and returned exit code 0. The results are in `evidence/gitleaks-history.txt` and `evidence/gitleaks-report.json`.

The EC2 workstation authenticates through its instance profile, LabRole, while the Vocareum console and temporary AWS CLI credentials use the voclabs identity. Obtaining AWS credentials in GitHub Actions requires a separate step, and the refresh script supplies the temporary voclabs session rather than the workstation's LabRole identity. These roles have different permissions, so an operation permitted locally is not necessarily permitted in CI. For example, iam:CreatePolicy succeeded under my workstation's LabRole, but this does not establish that the same permission is granted to voclabs. The unrelated Lab 3 check failed because its repository-level credentials were no longer available after Assignment 1 moved them into GitHub Environments. In contrast, the Lab 8 tfsec workflow needs no AWS identity because it analyzes Terraform configuration files without deploying resources.
